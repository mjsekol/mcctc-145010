# Template · Sprint Plan and Review
## 145010 Senior Capstone · Weeks 11-14, one per week

**Commit as:** `docs/improve/sprint-<n>.md`
**Due:** the plan on Monday, before the build period. The review on Friday, before the weekly
update is sent.

**Competencies this evidences:** 1.4.7 (productivity tools to optimize assigned tasks), 1.2.7
(problem-solving to determine next steps), 1.1.7 (critical thinking when making decisions), 2.9.5
(timeline and task breakdown, carried from the proposal into the build).

---

## Why this exists

**A one-week sprint ends with something you can show, or with an honest reason why not.** Either
way, you find out in the same week. The plan is where you promise a small thing. The review is
where you check whether you kept the promise, and adjust next week before it is too late.

**The Agile ceremonies live inside DMAIC's Improve phase.** Sprint planning, daily standup, the
demo, and the review are how this capstone runs them.

**The failure to avoid is a plan with more hours than the week.** You have roughly twelve hours of
class time plus Period 8. A plan for twenty is a plan to be behind by Wednesday.

## Sprint goals that usually work

| Sprint | Week | A goal that usually works |
|---|---|---|
| 1 | 11 | The walking skeleton, deployed and reachable: one thin path through every layer, running where it will finally run |
| 2 | 12 | The main task works end to end on the deployed system. Scope locked on Friday |
| 3 | 13 | The remaining in-scope requirements. Peer Code Review 1 |
| 4 | 14 | No new features. Finish, fix Review 1's must-fix findings, run the full test plan. Release candidate on Friday |

## Before you commit the plan · self-check

- [ ] The goal is one sentence the stakeholder would understand.
- [ ] The total hours fit the week.
- [ ] Every task has a "done when" someone else could check.
- [ ] You named what to cut first.
- [ ] After Week 12, every task traces to the scope lock statement.
